Why the preflight is exact

The preflight runs on complete, positive-weight eligible observations, using
the original FE key columns before rank dictionaries are constructed. One
GROUPING SETS query determines whether any group meets the requested removal
rule: singletons, constant-outcome binomial groups, or all-zero Poisson groups.
If no group qualifies, the existing recursive pruner would remove no rows and
perform no recursive round, so it can be skipped. If any group qualifies,
the unchanged recursive pruner runs and determines all removals and counts.

Compound FE keys use their separate SQL columns, never concatenated strings.
Quoted/Unicode string keys, shared grouping columns, all pruning modes,
positive constant Poisson outcomes and empty input are tested. More than
30 distinct grouping columns conservatively keeps the previous path.
Models with actual removals pay for one additional preflight query. DuckDB
and the other backends keep their previous execution paths.

Result-batching experiment (not integrated)

The prototype grouped FE summary rows into JSON arrays while carrying each
key with its values, so array ordering was irrelevant. Queries took 9.501
and 9.630 seconds versus 9.693 and 9.617 seconds for ordinary numeric rows.
The fetched JSON failed to parse in both repetitions through this ODBC path;
the underlying metadata/driver cause has not been established. These are
failed experiments, not valid fit times or successful transfer reductions.
No packed JSON-array transport was added to the production path.

The existing global-scalar JSON summary is distinct: it is small, retained,
and covered by the previously passing round-trip tests. Numeric FE moments
still use the verified numeric result path.
